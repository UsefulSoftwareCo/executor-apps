# Domo

Domo's public Platform API: DataSets (data, queries, PDP policies), Streams and executions, data accounts and account types, cards, pages and collections, users, groups, projects (lists, tasks, attachments), the audit log, embed tokens and simple JSON push. 87 tools, mounted under one key per API (`datasets`, `streams`, `accounts`, `cards`, `pages`, `users`, `groups`, `projects`, `activity`, `embed`, `simple`).

**Interface:** OpenAPI. Domo publishes one official OpenAPI document per resource in its documentation repository, https://github.com/DomoApps/domo-documentation-hub/tree/main/openapi/platform (also served on https://developer.domo.com). The token endpoint's own document (`authentication.yaml`) is not mounted; Executor performs the grant. The "product" (internal, instance-hosted) APIs in the same repository are not included: they live on each customer's `<instance>.domo.com` host and use a developer token, not the OAuth client.

**Auth:** OAuth 2.0 client credentials. Create an API client at https://developer.domo.com/manage-clients (sign in with your Domo instance name), choose its scopes (data, user, dashboard, account, audit, buzz) and paste the client ID and secret on the connect page. Executor exchanges them at `https://api.domo.com/oauth/token` with HTTP Basic client authentication and renews the token when it expires. No redirect URI is involved. No scope is requested, so the token carries every scope the client was granted; calls outside those scopes fail with 403.

**Gaps:** the health check lists one user, so the client needs the `user` scope for the account to verify, and the token carries no account identity, so connected accounts are not named. The Domo-hosted product APIs (alerts, beast modes, connectors, code engine, workflows) and the App Framework APIs are not covered. The token endpoint was not exercised with real credentials: it is documented as `GET` with query parameters, and Domo's own integrations record shows `POST` with a form body is accepted.
