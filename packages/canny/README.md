# Canny

Canny is a customer feedback platform. This package exposes 51 tools over its REST API: boards, categories, posts (create, update, status, board and category moves, merge, tags, Jira links), comments, votes, tags, users, companies, changelog entries, groups, ideas, insights, opportunities, status changes and Autopilot enqueue.

**Interface:** hand-written tools over the official REST API documented at https://developers.canny.io/api-reference (base `https://canny.io/api`; every endpoint is a POST with a JSON body). Canny publishes no OpenAPI document. Every endpoint and argument list was checked against the full reference page; all 51 tools map to a documented endpoint.

**Why not the MCP server:** Canny also runs an official remote MCP server (OAuth, S256 PKCE, client-ID metadata documents, no dynamic registration). `scripts/mcp-probe.ts` reports verdict `oauth`. Executor can use CIMD where the host publishes a client metadata document (Executor Cloud does; the local test server does not, and its `oauth/setup` check returned `client-required`). An earlier version of this README wrongly said Executor cannot complete this flow. Two further facts: the server's protected-resource metadata names the resource `https://api.canny.io/api/mcp/v1`, so `oauth2({ discover: "https://canny.io/api/mcp/v1" })` fails with `resource_mismatch`, while the `api.canny.io` URL discovers cleanly. Its tool list sits behind OAuth and was not enumerated (no real account may be connected here), so a tool-count comparison with this package's 51 was not possible. REST was kept because it covers every documented endpoint with a plain secret key that works on any host; revisit if the MCP turns out to expose more.

**Auth:** secret API key only on the REST API. A company owner or admin finds the key under Settings, API (https://canny.io/admin/settings/api). The package sends it as the `apiKey` field of the JSON body, as Canny documents. The only host is `canny.io`. The health check is `POST /v1/boards/list` and decodes no fields.

**Known gaps:** write tools take Canny user ids (`authorID`, `voterID`, `changerID`), which you look up with `users.retrieve`. Ambiguity: the docs list `users/delete` with argument `id` but their curl example sends `userID`; the package follows the argument table (`id`, the Canny id) and this was not tested against the live API. `posts/change_status` marks `commentValue` and `commentImageURLs` without "(optional)" in the docs, but the example omits them, so they are optional here. `ideas.list` takes `filtering` and `sort` as free-form objects. `users/find_or_create` is documented but not exposed (superseded by `create_or_update`). Rate limits (5 to 20 requests per second by plan) apply.
