# Booking.com

Covers the Booking.com Demand API (v3.1): accommodation and car-rental search, availability, details and reviews, location and payment reference data, order preview/create/modify/cancel, and partner-guest messaging with attachments. 39 tools.

**Interface:** the official Demand API OpenAPI 3.1 document, published by Booking.com at https://developers.booking.com/_bundle/demand/docs/open-api/demand-api.json (production server `https://demandapi.booking.com/3.1`; the spec's sandbox server is not used). Booking.com also runs an official Demand API MCP server (`https://demandapi-mcp.booking.com/v1/sp/mcp/`, headers `x-booking-affiliate-id` and `x-booking-authorization`); it is limited to approved partners and its tool list cannot be enumerated without credentials, so the OpenAPI document is used.

**Auth:** Demand API token plus Affiliate ID (`apiKey`, two secret fields). The token is sent as a Bearer token and the Affiliate ID as the `X-Affiliate-Id` header on every call; Booking.com's getting-started text says the API "requires authentication using your Affiliate ID and token credentials". The published OpenAPI document declares only the bearer scheme and lists `X-Affiliate-Id` as a per-operation parameter (and omits it on `/orders/modify`), so `openapi.ts` patches the document to declare it as a second apiKey scheme and drops the per-operation parameter. Demand API access is partner-gated: obtain the token and Affiliate ID from the Booking.com Demand API portal or your account manager (https://developers.booking.com/demand). There is no user-created OAuth app. The health check calls `/common/languages` with both credentials, requires a 2xx and decodes the `data` array, so a missing or wrong token or affiliate id fails it; it could not be run against a live partner account here.

**Approvals:** all operations are POSTs, so approval is the default: only the explicit read-only set (accommodation and car search/details/reviews, common reference data, `orders.preview`, `orders.details*`, conversations, latest messages, attachment metadata/download) runs without it. Order create/modify/cancel, sending messages, confirming receipt and uploading attachments require approval. `orders.preview` is treated as read-only because the vendor describes it as returning the final price and policies for the products passed in; it does not create an order.

**Known gaps:** the Connectivity (XML supply, machine-account basic auth), Metasearch Connect and Data Portability APIs are separate surfaces and are not included. Flights and attractions are not in the published OpenAPI document.
