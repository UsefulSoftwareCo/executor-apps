# Optum Real

Optum Real payer-provider APIs from Optum (UnitedHealth Group). Medical: pre-service eligibility, patient benefit check, claim pre-check, claim inquiry, claim actions, document search, authorization and referral submission, and FHIR prior authorization (Da Vinci CRD/DTR/PAS). Dental: pre-care eligibility and estimates, claim submission, claim status, and attachments. 31 tools in total across 13 APIs.

**Interface.** OpenAPI. The 13 official OpenAPI documents come from the Optum developer portal ("Download OpenAPI Spec" on each API's Overview page, https://developer.optum.com/optumreal-medical/ and https://developer.optum.com/optumreal-dental/). They are vendored unchanged in `specs/` because the portal rate limits downloads and its document ids change with every revision; refresh them from the portal when Optum publishes a new version. The specs list the sandbox origin, so the app swaps in `https://apigw.optum.com` for production accounts. Several APIs are GraphQL-style payloads sent over a single POST endpoint, so those tools take the request document as their body. POST lookups (eligibility, benefit check, claim inquiry, claim status, document search, search attachments, pre-checks, and the prior-auth questionnaire and inquiry reads) are marked as queries and run without approval. They are read-only but do return PHI, so that is a deliberate choice. Every other mutation, including all claim actions, referrals, dental claim submissions and prior-auth submissions, has no override and requires approval.

**Auth.** OAuth 2 client credentials, two methods: `sandbox` (`https://sandbox-apigw.optum.com/apip/auth/sntl/v1/token`) and `production` (`https://apigw.optum.com/apip/auth/sntl/v1/token`). Create an application on the Optum developer portal (https://developer.optum.com), subscribe it to the Optum Real APIs and complete API onboarding with Optum; the portal then shows the client ID and secret to enter on the connect page. Executor exchanges them for a bearer token and renews it. No OAuth scope is requested (`scopes: []`): the medical specs declare scopes such as `read_txn` and `create_txn`, but the dental specs declare none, and I could not find Optum documentation requiring a scope on the token endpoint. This is unverified against a live Optum application; if the token endpoint rejects scope-less requests, add the specs' scopes. There is no browser redirect, so no redirect URI is needed.

**Known gaps.** Access to real data requires Optum onboarding and payer enablement, which this package cannot do. The APIs have no read-only account endpoint, so the connection check calls the documented dental eligibility `healthcheck` GET with the account's token and ignores the body. The Optum Real file manager and Da Vinci bulk data export APIs listed on the portal publish no downloadable OpenAPI document and are not included. Health check endpoints that Optum documents per API are included where the spec has them.
