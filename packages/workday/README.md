# Workday

Workers, supervisory organizations, Report-as-a-Service custom reports and any other REST endpoint of one Workday tenant.

**Interface:** hand-written tools over Workday's REST API, `https://{host}/ccx/api/{service}/{tenant}/...` (default service `v1`), plus custom reports at `https://{host}/ccx/service/customreport2/{tenant}/{owner}/{report}`. Workday publishes no public OpenAPI document: the API Directory and its Swagger files live inside each tenant (and Workday Community, behind login), and the Graph API schema is per tenant, so nothing can be compiled ahead of time. Tools: `workers.list/get/directReports/history/timeOffEntries/paySlips`, `organizations.supervisoryOrganizations/supervisoryOrganization`, `reports.run`, and the generic `api.get` and `api.send` for any endpoint your tenant's API Directory lists (for example `staffing/v6`). Writes (`api.send`) require approval. Paths for workers, workers/{id}, timeOffEntries, paySlips, directReports and supervisoryOrganizations match Workday Common v1 as seen in community integrations (directReports is the Common v1 getWorkerReports operation); `workers.history` (`/workers/{id}/history`) could not be confirmed, so use `api.get` against your tenant's API Directory if it returns 404. Nothing was exercised against a live tenant. `reports.run` replaces spaces in the report name with underscores, per Workday's RaaS URL rule; copy the exact URL from the report's Web Service > View URLs action if a name has other special characters. `api.send` returns `null` for empty 2xx bodies such as 204.

**Auth:** API client with a refresh token. In Workday, run the task Register API Client for Integrations (or Register API Client), choose "Non-Expiring Refresh Tokens", select the functional areas you need, then use Manage Refresh Tokens for Integrations to generate a token for a user. The connect form asks for the host and tenant (shown at the top of View API Clients, for example `wd2-impl-services1.workday.com` and `acme`), the client ID, the client secret and the refresh token. The package exchanges the refresh token at `https://{host}/ccx/oauth2/{tenant}/token` (HTTP Basic client credentials) and sends the access token as a bearer token to that host only. Authorization-code OAuth is not offered because its authorize and token URLs are per tenant, which a static OAuth declaration cannot express (the framework's `oauth2` declares `authorizationUrl` and `tokenUrl` at provider level, not per account). This is an explicit decision: Workday does support authorization-code API clients.

**Known gaps:** Workday SOAP web services (Get_Workers etc.), the Graph API (`/ccx/api/graphql`; schema is per tenant, not publicly documented, and not verified, so it is not wrapped), WQL and Adaptive Planning (a separate product with its own API) are not wrapped. Which endpoints work depends on the functional areas granted to the API client and the security policy of its user. Only the single refresh-token method is supported.


**Official MCP:** Workday's MCP offering (Agent Gateway) is tenant-specific and not public, so no MCP server is used.
