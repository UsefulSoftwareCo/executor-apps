# Clientary

Clientary client management and billing: clients, contacts, leads, projects, tasks, hours (time tracking), invoices, payments, payment profiles, estimates, expenses and staff. 67 tools.

## Interface

Hand-written tools over the official Clientary API v2 (https://www.clientary.com/api). Clientary publishes no OpenAPI document (the only spec is a third-party one on Jentic, which is not used), so each documented endpoint is declared in `index.ts`. Lists are paged with `page`, the documented paging input (`page_size` is accepted only where the vendor documents it: contacts and projects; the tasks, hours and expenses lists document no paging input); writes take a `body` of the resource's attributes and the tool wraps it in the resource key Clientary expects.

## Auth

API token only. The vendor does document OAuth 2.0 (authorization code with PKCE; RFC 8414 metadata at https://www.clientary.com/.well-known/oauth-authorization-server: authorize `https://www.clientary.com/oauth/authorize`, token `https://www.clientary.com/oauth/token`, dynamic client registration, single scope `all`; requests use `Authorization: Bearer <token>`), but it is not wired yet. The API host is per account (`https://{subdomain}.clientary.com/api/v2`), an Executor OAuth account carries only the access token, and the vendor documents neither a token-response field nor an endpoint that reveals the account subdomain, so an OAuth account could not address its API host. Adding `oauth2({ discover: "https://www.clientary.com", scopes: ["all"], request: ({ access_token }) => bearer(access_token) })` needs a way to supply the subdomain per connection. When it is added, the redirect URI to register with Clientary is the one Executor shows on the connect page. (The OAuth metadata also lists a resource at `https://www.clientary.com/mcp`; its tools were not verified.)

Every user has their own token (Settings, API in your Clientary account), and requests are attributed to that user. Enter your account subdomain (the `acme` in `acme.clientary.com`) and the token; the token is sent as both the HTTP Basic username and password.

## Gaps

- OAuth is documented by the vendor but not wired (see Auth).
- Recurring invoices are reachable only through the invoices generated by one (`invoices.listForRecurring`).
- Resources in the vendor's API docs that are not covered: Comments, Contracts, Proposals, Retainers, Templates, Reports, Recurring Schedules (beyond `invoices.listForRecurring`), Recurring Time and Assistants.
- Body shapes for writes follow the vendor docs and are not validated by the tool. Wrapper keys: hours use `project_item`, contacts use `client_user` (the vendor shows it for both create and update; not checked against a live account). Mutations require approval.
- No official OpenAPI exists, and no official MCP server was verified.
