# Brilliant Directories

Manage a Brilliant Directories site: members, posts, leads, reviews, top and sub categories, membership plans, pages, redirects, menus, forms, widgets, email templates and the other resources the site's REST API exposes. Every mutation asks for approval.

**Interface.** The site's REST API at `https://<your site>/api/v2/...`, described by Brilliant Directories' own OpenAPI 3.1 document, published in the vendor's repository, pinned to commit `c9e5fd90a803b7849a8174244def8b58c663feaa` (the latest commit touching the file at the time of writing; bump deliberately): https://raw.githubusercontent.com/brilliantdirectories/brilliant-directories-mcp/c9e5fd90a803b7849a8174244def8b58c663feaa/mcp/openapi/bd-api.json (172 tools, 95 of them mutations, none skipped). The vendor also runs a hosted MCP server at `https://brilliantmcp.com` over the same API; it is not mounted because the OpenAPI document already covers it.

**Auth.** API key only; BD offers no OAuth. In BD Admin go to Developer Hub > Generate API Key, then enter the key together with your site URL exactly as the site loads in a browser (`https://www.mysite.com`: include `https://`, include `www.` if the site uses it, no trailing slash). The key is sent as the `X-Api-Key` header (the header name comes from the securityScheme in the vendor's OpenAPI document; the support article does not name it) to your site's origin only. New keys start with Standard Endpoints enabled (members, leads, posts, reviews, widgets and similar) and Advanced Endpoints disabled: for the other resources, open the Actions menu for the key, choose Configure Permissions, enable the Advanced Endpoints you need and select Save Permissions, or those tools are denied (the vendor does not document the status code). Leaving a `delete` action off prevents deletions.

**Known gaps.** Recorded exception to the AUTHORING rule to declare `hosts`: each site has its own domain, and the framework's `hosts` on a provider is static and provider-level, so there is no way to declare a per-account host. Without `hosts` the key reaches app code as a raw secret rather than a handle; the app only sends it to the origin of the site URL on the account (`allowedOrigin` is set per account). This is a framework gap to report: per-account hosts derived from a plain field. Endpoints are rate limited by the site. Request bodies are form-encoded as the API expects.
