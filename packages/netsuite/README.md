# NetSuite

Customers, vendors, contacts, employees, sales and purchase transactions (sales orders, invoices, estimates, cash sales, credit memos, payments, purchase orders, vendor bills, item fulfillments and receipts, expense reports, journal entries), inventory items, opportunities, support cases, tasks, projects, the chart of accounts, subsidiaries, departments, classes, locations and currencies of a NetSuite account, plus SuiteQL queries and any other record type, custom records included.

**Interface:** hand-written tools, about 166 in total, over NetSuite's SuiteTalk REST Web Services (https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/chapter_1540391670.html): the REST Record API (`/services/rest/record/v1`, with `!transform` and the metadata catalog) and the SuiteQL endpoint (`/services/rest/query/v1/suiteql`). NetSuite publishes no public OpenAPI document: the OpenAPI 3 description of the record API is generated per account (and per its customizations) and needs credentials, and every account has its own host (`https://<account-id>.suitetalk.api.netsuite.com`). NetSuite's AI Connector MCP server is also per-account and OAuth-only with per-account endpoints, which Executor cannot declare statically. There are 31 typed record groups (`customers`, `salesOrders`, ...) with list, get, create, update and delete, a generic `records` group (list, get, create, update, upsert by external id, delete, sublist, transform, metadata) that reaches any record type, `suiteql`, and a `rest` escape hatch for other endpoints. Record mutations always ask for approval; reads and SuiteQL do not. The `rest` escape hatch always asks, even for GET, because it can reach mutating endpoints. `suiteql` takes an optional `params` array for `?` placeholders.

**Auth:** token-based authentication (TBA, OAuth 1.0a with HMAC-SHA256). In NetSuite:

1. Setup > Company > Enable Features > SuiteCloud: enable REST Web Services and Token-Based Authentication.
2. Setup > Integration > Manage Integrations > New: create an integration record with Token-Based Authentication checked (and TBA authorization flow / OAuth 2.0 boxes off). Copy the consumer key and secret, shown once.
3. Create a role with the REST Web Services and Log in using Access Tokens permissions plus the record permissions you want the tools to use, assign it to a user, then Setup > Users/Roles > Access Tokens > New for that integration, user and role. Copy the token ID and secret, shown once.
4. In Executor enter the account ID (Setup > Company > Company Information; sandboxes look like `1234567_SB1`), the consumer key and secret, and the token ID and secret.

The four credentials are `raw` fields because every request has to be signed with them; the app signs requests itself and sends them only to `*.suitetalk.api.netsuite.com`.

**Vendor signing facts checked against Oracle's docs** (section_1534941088.html, section_1534941295.html): "As of 2023.1, the support ended for the HMAC-SHA1 signature method." The signature is "a base64 value of the HMAC-SHA" over the base string; the key is "the URL-encoded values for consumer secret and token secret, with the ampersand character (&) as the delimiter"; query parameters are merged with the `oauth_*` parameters and sorted into the base string, `realm` is excluded from it, and "TBA uses percent encoding" (RFC 5849 section 3.6). The header is `Authorization: OAuth realm="<account>", oauth_consumer_key=..., oauth_signature_method="HMAC-SHA256", ...`, and the account ID is the subdomain of `suitetalk.api.netsuite.com`. Not confirmed from vendor text: the sandbox forms (realm `1234567_SB1` uppercase with underscore; host `1234567-sb1` lowercase with hyphen). Those follow common NetSuite practice; the Oracle pages fetched only show numeric production IDs. Treat signing as unverified until one signed read-only call succeeds against a sandbox with real credentials (none was made).

**OAuth 2.0 (framework gap, not offered):** Oracle calls OAuth 2.0 the preferred method, and says that as of 2027.1 no new TBA integrations can be created for REST web services (existing ones keep working). Executor's `oauth2` takes only static `authorizationUrl` and `tokenUrl` strings (`contracts/provider.d.ts`), but NetSuite's endpoints are per account (`https://<account>.app.netsuite.com/app/login/oauth2/authorize.nl` and `https://<account>.suitetalk.api.netsuite.com/services/rest/auth/oauth2/v1/token`, scope `rest_webservices`). Until the framework supports account-templated OAuth endpoints, only TBA is available, so this package is status `blocked` for OAuth and new TBA integrations will stop being creatable in 2027.1.

**Icon exception:** NetSuite publishes no icon in Simple Icons, and its Oracle brand and press pages could not be fetched (403) so a NetSuite-only mark or SVG could not be ruled in or out. The icon is a 256x256 PNG of the Oracle NetSuite lockup (ORACLE wordmark above NetSuite) from Wikimedia Commons (`2024_NetSuite_logo.png`), on a baked-in white square. It is a documented exception to the no-parent-logo rule and should be replaced by an official NetSuite-only mark when one is found. The dark variant is the same white tile, not a true dark variant.

**Known gaps:** File Cabinet upload/download (SuiteScript RESTlets), SOAP SuiteTalk and RESTlets are not covered, except that `rest` reaches any path under `/services/rest/`. Typed record names follow the REST record catalog; use `records.metadata` to confirm a record exists in your account. No real account was connected during authoring, so request signing and the endpoints were checked against the vendor's documentation but not against a live account.
