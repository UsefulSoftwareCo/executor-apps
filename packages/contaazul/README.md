# Conta Azul

Conta Azul is a Brazilian cloud ERP. This package covers its public API: financial events (receivables and payables, installments), financial accounts and balances, categories, cost centers, transfers, sales, people (customers, suppliers, carriers), products and services, fiscal invoices and contracts. Tools are mounted under six keys: `financial`, `sales`, `people`, `products`, `invoices` and `contracts`.

**Interface:** OpenAPI. Conta Azul publishes one official OpenAPI 3 document per API area on https://developers.contaazul.com (for example `https://developers.contaazul.com/_bundle/docs/financial-apis-openapi.json?download`); all are served from `https://api-v2.contaazul.com`. Every mutation asks for approval. The six documents declare 56 operations in total (financial 19, sales 9, contracts 3, people 10, products 11, invoices 4; each compiles to one tool per operation with none skipped; the financial document has 17 paths but 19 operations, since some paths carry GET and POST or GET and PATCH); the spec files are live, so counts follow the vendor.

**Auth:** OAuth 2.0 authorization code. Conta Azul has no shared client, so each user creates an application in the Developer Portal (https://developers-portal.contaazul.com, "Criar uma aplicacao"), choosing Development or Production, and copies the client ID and client secret. Register the Executor redirect URI shown on the connect page as the application's redirect URL (Development apps use `https://www.contaazul.com` for testing and return fictitious data; Production apps need their own redirect URL). Sign in with a Conta Azul ERP account, not the Developer Portal account. Scopes are fixed: `openid profile aws.cognito.signin.user.admin`. Access tokens last one hour; refresh tokens rotate on every refresh. The client authenticates with HTTP Basic.

Note on endpoints: the token endpoint is the vendor-documented `https://api-v2.contaazul.com/oauth/token` (HTTP Basic, form body; refresh tokens rotate). The vendor documents the authorization page as `https://login.contaazul.com/#/oauth/authorize`, a fragment URL whose query string would land before the `#`, so Executor cannot build it. The package instead uses `https://auth.contaazul.com/login`, the hosted sign-in page; it exists (it redirects) but could not be exercised end to end without a real account, so treat the authorization step as unverified. The vendor requires a `state` parameter; Executor sets `state` itself for every OAuth flow. The vendor's docs never mention PKCE; Executor's PKCE behavior for declared endpoints was not confirmed, so if sign-in rejects `code_challenge`, that is the cause. The account health check calls `GET /v1/pessoas/conta-conectada` and only checks that it succeeds (the vendor's schema marks no field as required), so no external account id is recorded.

**Known gaps:** Webhooks do not exist (the API must be polled). The documentation sidebar also lists Services, Quotes and Capture areas without published OpenAPI documents; they are not covered.
