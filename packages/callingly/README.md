# Callingly

Callingly lead response management: create a lead and trigger an instant call, list and fetch calls (with recordings and transcripts), list, update and delete leads, send SMS, and manage teams, team agents, agents and their schedules, agency clients and webhooks. 31 tools.

**Interface:** hand-written tools over the documented REST API (`https://api.callingly.com/v1`, reference at https://help.callingly.com/article/38-callingly-api-documentation), plus the vendor's official remote MCP server (`https://api.callingly.com/mcp`, https://callingly.com/features/mcp) mounted under the `mcp` group. The MCP server has 8 tools (make_dispatch_call, make_ai_call, send_sms, schedule_sms, add_to_sequence, get_recording, schedule_call, query_reports) and adds capabilities the REST API lacks (AI calls, sequences, scheduled SMS, reports). REST is the primary surface because Callingly publishes no OpenAPI document (the only copy found is third-party), so every documented REST endpoint is wrapped directly. All mutations (REST and non-read-only MCP tools) require approval.

**Auth:** two methods.
- `apiKey`: sent as `Authorization: Bearer <key>`. Create it in the Callingly dashboard under Settings, API Keys, "Add API Key"; the key is shown once. This is the only method the REST API documents, so REST tools are only mounted for API-key accounts. Agency accounts can pass `account_id` on calls.create, agents and team creation to act for a client.
- `oauth`: the MCP server advertises OAuth (probe verdict `oauth`: protected-resource metadata at `https://api.callingly.com/.well-known/oauth-protected-resource/mcp`, authorization server `https://api.callingly.com`, dynamic client registration at `/oauth/register`, scope `mcp:use`, S256 PKCE). OAuth accounts get the `mcp` group only. The redirect URI is Executor's callback shown on the connect screen.

The vendor's MCP marketing page says to paste a `clly_live_` API key as the bearer token, while the endpoint's own 401 challenge points to OAuth. We could not test a valid key (no credentials in this environment), so the key-as-MCP-bearer claim is untested: API-key accounts send the key to the MCP server as the page says, and OAuth is the verified-by-probe method. If the key is rejected, use an OAuth account for MCP tools.

**Icon:** the Callingly speech-bubble handset mark, cropped from the vendor's official SVG logo (`https://callingly.com/img/marketing/callingly.svg`); it is not in Simple Icons.

**Known gaps:** the docs do not describe the `PUT /teams/{id}` body, so `teams.update` takes a free-form `settings` object. `PUT /webhooks` is documented without an id and with name, event and target_url marked required; the tool sends `PUT /webhooks/{id}`, a path inferred from the other by-id routes and unverified. Requiredness is mostly undocumented (only scheduled_at is marked optional): the required inputs on calls.create (team_id, phone_number), teams.create (name), agents.create (fname, phone_number), clients.create and leads.update (id) are inferred. `account_id` is only exposed where documented (POST /calls, POST /teams, POST /agents, GET /agents). Pagination, rate limits and error formats are undocumented. The API-key health check lists teams; the OAuth health check initializes the MCP server.
